**Production:** Disabled  
**Financial execution:** Disabled  
**Custody/signing:** Not configured

## 1. Objective

Provide a governed corporate treasury subsystem for tracking and reconciling fiat cash and EVM stablecoin positions across multiple accounting currencies. The subsystem is a treasury ledger and visibility layer; it is not itself a bank, exchange, custodian, payment rail, money transmitter or stablecoin issuer.

Initial accounting currencies: **ZAR, USD, EUR**. Currency support is a ledger/reporting capability, not evidence that a bank or off-ramp supports deposits or withdrawals in each currency.

Initial stablecoin asset candidates: **USDC, USDT, DAI and EURC**. A symbol is not a token identity. Each supported asset must be registered by chain ID, verified contract address, decimals, issuer/administrator, reserve/redemption documentation, and review date. No token contract is pre-approved by symbol alone.

## 3. Deployment and network profile

### Default sandbox

- Local EVM simulator (e.g. Anvil/Hardhat) with locally deployed mock ERC-20 contracts for deterministic unit and integration tests.
- Chain ID and mock contract addresses are generated by the test fixture; never copy mock addresses into a production registry.
- No public-chain transaction broadcasting in the default test suite.
- Optional Sepolia read-only RPC smoke test using the existing Alchemy app, after the RPC URL is supplied through a secret manager/environment variable.
- A separate test-only wallet may be introduced only after its owner, address, custody method and zero-mainnet-funds assertion are verified.
- No production chain is selected as a transaction target.

### Production network posture

Production EVM networks are **inventory-only**. Even though the Alchemy app lists mainnets, this configuration does not authorise wallet access, contract calls that mutate state, approvals, transfers, swaps, bridging, staking, lending or withdrawals.

## 4. Functional components

1. **Treasury account registry** — legal entity, account type, currency, provider, status and evidence reference.
2. **Watch-only wallet registry** — chain ID, address, owner/custodian, purpose and verification status; no private keys.
3. **Token registry** — chain-specific contract address, decimals, issuer, asset classification, verification evidence and allowlist status.
4. **Double-entry ledger** — balanced journal entries, immutable postings, reversals rather than edits, and separate pending/settled states.
5. **Valuation engine** — timestamped FX and token price observations, source, quote age, spread and confidence; never treat a peg as guaranteed.
6. **Cash-flow forecast** — expected inflows/outflows, maturity dates, obligations and liquidity buckets.
7. **Reconciliation engine** — compare bank statements, provider statements, chain events and internal ledger; unmatched items remain exceptions.
8. **Risk and compliance controls** — counterparty, issuer, chain, depeg, liquidity, sanctions/AML screening evidence, concentration and operational limits.
9. **Approval workflow** — maker/checker separation, amount thresholds, beneficiary allowlists, expiry, simulation evidence and separate execution authorisation.
10. **Audit and reporting** — append-only events, evidence hashes, daily close, entity/currency reports and exception queues.

## 5. Required ledger invariants

- Every posted journal balances to zero within its single ledger currency.
- Cross-currency movement uses explicit FX clearing accounts and a recorded rate/source/time; do not mix unlike currencies in one balancing total.
- Amounts are stored as integer minor units or exact decimal strings; never binary floating point.
- Token quantity uses integer base units plus verified decimals.
- Chain ID and token contract are part of every on-chain asset identity.
- Transaction hash + chain ID + log index is an idempotency key for indexed events.
- Reorgs and reversals create compensating records; posted records are never silently overwritten.
- Pending, confirmed, finalised, failed and reversed states remain distinct.
- A price feed is not a redemption guarantee; show market value separately from redeemable cash value.
- Unknown token, unknown chain, stale price, unverified wallet or unresolved reconciliation exception blocks any proposed execution.

## 6. Approval and execution policy

All capabilities start disabled except local test simulation and approved read-only data retrieval.

| Operation | Initial policy |
|---|---|
| Read configured network metadata | Allowed |
| Read-only chain/token balance lookup | Requires a specifically supplied public wallet address |
| Local mock-token tests | Allowed in isolated local simulator |
| Sepolia read-only query | Optional; no signing |
| Create wallet or generate key | Disabled |
| Sign transaction | Disabled |
| Token approval / allowance increase | Disabled |
| Transfer, swap, bridge, mint, burn or redeem | Disabled |
| Bank deposit, payout or withdrawal | Disabled |
| Aave supply, borrow, repay, withdraw or stake | Disabled |
| Production deployment or provider-account change | Separate explicit approval required |

An approval record is not an execution command. Any future executor must independently validate the approved request digest, target chain, contract, amount, recipient, expiry and policy version immediately before signing.

## 8. Test plan

### Unit tests
- Currency precision and rounding per ISO currency.
- Token decimals and base-unit conversion.
- Journal balancing and cross-currency clearing.
- Price freshness and missing-price blocking.
- Chain/contract identity separation.
- Idempotent chain event ingestion.
- Reorg and compensating-entry handling.
- Limit and maker/checker policy evaluation.

### Integration tests (local simulator only)
- Deploy mock USDC/USDT/DAI/EURC-like ERC-20 contracts to a disposable local chain.
- Index mint, transfer and burn events from test fixtures.
- Reconcile indexed events against generated statements and ledger entries.
- Verify no external RPC transaction submission occurs.
- Verify no production credentials are loaded by tests.

### Security tests
- No private key or seed phrase in repository, logs, config or audit metadata.
- Read-only service cannot invoke signing or mutation methods.
- Unapproved request, altered request digest, expired approval and wrong chain are denied.
- Cross-organisation and cross-entity reads are denied.
- Audit records cannot be updated or deleted by application runtime roles.
